# WHO recommendation / WHO PQ listing — drawn in parallel, not in sequence

Branch: `fix/sep9-feedback-parallel`. Implements the reviewer's Sep 2026 suggestion
in full ("Option A": data model + every page variant + the ontology + the
validator), on top of the 5 already-fixed items (WHO recommendation / WHO PQ
listing relabeling, "current bottleneck," spatial emanators removed, "Recent
dashboard updates"), which this branch also carries as uncommitted working-tree
state — see `docs/reviewer-feedback-sep-2026.md` for those.

**Not done: Meg and Lisa's sign-off.** The reviewer explicitly asked for it
before committing to this schematic — it's a mild editorial/advocacy statement
("these should run in parallel"), not a pure layout call. This branch builds
the option so there's something concrete to show them; it should not go out
before they've weighed in.

## The schema decision

Rejected: reindexing the 8-slot `stages[]` array so the two WHO stages sit at
one position. `currentStage`, every `milestones[]`/`journey[]` entry, the
changelog, and the whole ontology generator point into `stages[]` by position
— remapping it is a breaking change across 4 products × 2 datasets for no
real gain.

Instead, added one new, optional, additive field to `meta`:

    "stageColumns": [
      { "stages": [0] }, { "stages": [1] }, { "stages": [2, 3] },
      { "stages": [4] }, { "stages": [5] }, { "stages": [6] }, { "stages": [7] }
    ]

Groups stage indices into *display* columns; a column listing more than one
index is a parallel pair with no defined order. `stages[]`, `currentStage`,
and every index-keyed reference are completely unchanged — this is a pure
rendering/presentation instruction layered on top. Absent `stageColumns`
(e.g. a future dataset that hasn't added it), every renderer falls back to
one stage per column — today's behaviour, byte for byte.

`scripts/validate-data.js` enforces it: flattened in column order,
`stageColumns` must equal `[0, 1, ..., nStages-1]` exactly — grouping may
merge adjacent indices but never reorder or drop one. Tested against a
deliberately scrambled `[3, 2]` column and confirmed it's rejected.

## What actually changed, and why it's more than a relabel

**The per-product stage rail** (dashboard + index/option-b/story/widget, all
six page variants): the two WHO stages now render stacked in one column with
a small "no fixed order" caption between them, instead of side by side with
an implied arrow. `option-b.html`'s comparison matrix — a different layout
entirely (grid rows, not a horizontal stepper) — got the equivalent: the two
stages merge into one row with two dots per product instead of two rows.

**A real bug this uncovered:** the "is the incoming connector done" check
used to read `stages[i-1].status`, so the *second* WHO stage's bar quietly
depended on the *first* one being done — the code was itself asserting an
order between them that doesn't exist. Fixed by a `preBoundaryDone` helper
that looks at the column *before the group*, not at index i-1: both WHO
stages now correctly gate only on Regulatory approval, independent of each
other. (Doesn't change anything visible today — both are "done" for every
tracked product currently in the pair — but it was a live latent bug, now
correct in the general case.)

**The actual-timeline SVG (dashboard only) — this is the piece the reviewer
actually reacted to.** It used to connect real-year points strictly by
adjacent index, so ASPY's WHO PQ listing (2012) connecting from WHO
recommendation (2022) drew a dashed "dipping back" line with a tooltip
reading "these gates were not cleared in pathway order" — the exact visual
the reviewer flagged as a typo. Rewired to connect *column to column*: no
line is drawn between the two WHO stages at all (there's no "before" or
"after" to violate), and each instead fans independently to/from its real
neighbouring column. Verified directly against the real data:

  - ASPY now draws: Regulatory approval (2012) → WHO recommendation (2022,
    normal), and Regulatory approval (2012) → WHO PQ listing (2012, normal,
    0 years). The false "out of order" dip is gone.
  - DHA–PPQ's *genuine* inversion is untouched and still flagged: Regulatory
    approval (2011) → WHO recommendation (2010) still dips back and still
    explains itself, because stages 1 and 2 are in different columns — this
    is a real sequence anomaly, not a parallel pair, and should keep reading
    as one.

This is the strongest evidence for the reviewer's original argument: DHA–PPQ
recommended a treatment before it even had stringent regulatory approval,
which the fixed left-to-right board was quietly implying couldn't happen.

**The ontology.** `ontology/launch-data.jsonld` (generated by
`scripts/build-ontology.js` from `data/products.js`) now carries a symmetric
`concurrentWith` relation between `launch:stage-2` and `launch:stage-3`,
generated from `stageColumns`. `ontology/launch.ttl` (hand-authored; NOT
generated) gained the `launch:concurrentWith` property definition and a
corrected `PathwayStageScheme` definition. `ontology/index.html` is generated
from `launch.ttl` by `build-ontology-page.js` — it is never hand-edited
(confirmed by that script's own header comment); an earlier hand-edit to it
from the task-1/2 relabeling pass was reverted and the file regenerated
properly from the corrected `launch.ttl` instead, so it no longer drifts from
its source.

## Follow-up: the fork's corners are square, not rounded

10 Sep 2026, on client request — the fork read as a rounded *container* drawn
around the pair rather than as a bar that splits and rejoins. Removed the four
`border-*-radius` declarations on the `.stagegroup` elbows and the `14px`
`border-radius` on `.pathgroup`, so the strip and the row match.

`--sg-r` (9px) was doing double duty: the corner radius *and* the elbow's
horizontal run, which is also what `.bar.pre`/`.bar.post` margins key off. Only
the radii were dropped; the variable survives as the run, and its declaration
now says so. Do not reintroduce `border-radius` from it — the geometry breaks
if the run goes to 0.

Squaring them exposed a defect the radius had been hiding: **the corners did
not actually meet.** A border paints *inside* its box edge, so a `3px`
`border-top` puts its whole stroke below the box's top line, while `.bar` is
centred on the marker's centreline — leaving the two 1.5px apart, a half-stroke
step at every corner. The arc had blurred it; a right angle showed it.

Fixed by making the elbow box half a stroke taller,
`height: calc(var(--sg-arm) + var(--sg-w) / 2)`. Each elbow is anchored at its
spine end (`bottom` for `.sg-top`, `top` for `.sg-bottom`), so the extra height
moves only the free edge outward and the stroke ends up straddling the
centreline. The stroke weight is now `--sg-w` instead of `3px` repeated eight
times, because the fix depends on it: **`--sg-w` must equal `.stage .bar`'s
height** or the step comes back.

Verified by measurement, not by eye — cropped screenshots proved unreliable
here. Against the marker rect as ground truth, both branches report
`markerMid == barMid == elbowStrokeMid` (delta `0.00px`), and horizontally the
elbow's run ends exactly where `.bar.pre` begins. All four elbows report
`border-radius: 0px`; `.pathgroup` reports `0px`.
